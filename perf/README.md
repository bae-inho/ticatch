# 성능 측정

k6로 좌석 선점과 결제에 부하를 걸고, 끝난 뒤 데이터 정합성을 확인한다. 측정 환경과 결과는 [docs/performance.md](../docs/performance.md)에 남긴다.

## 처음 한 번 준비

1. Docker Desktop을 켜고 PostgreSQL을 띄운다.

   ```bash
   docker compose up -d
   ```

2. 측정용 DB를 만든다. 측정할 때마다 데이터를 지우므로 개발용 DB(`ticatch`)와 나눈다. `reset.sql`은 `ticatch_perf`가 아니면 실행을 거부한다.

   ```bash
   docker compose exec postgres createdb -U ticatch ticatch_perf
   ```

3. k6 이미지를 받는다. 결과를 비교할 수 있도록 버전을 고정한다.

   ```bash
   docker pull grafana/k6:1.3.0
   ```

## 측정 순서

1. 앱을 빌드하고 측정용 DB로 띄운다. 스키마는 Flyway가 만든다.

   ```bash
   ./gradlew bootJar
   ```

   ```bash
   java -jar build/libs/ticatch-0.0.1-SNAPSHOT.jar --spring.datasource.url=jdbc:postgresql://localhost:5432/ticatch_perf
   ```

2. 워밍업을 한 번 돌린다. JVM은 처음 실행하는 코드를 느리게 돌리므로, 측정 전에 같은 경로를 미리 실행해 둔다.

   ```bash
   perf/run.sh warmup
   ```

3. 시나리오마다 3번씩 돌리고 중앙값을 기록한다.

   ```bash
   perf/run.sh rush
   ```

   ```bash
   perf/run.sh steady
   ```

`run.sh`는 한 번 돌 때마다 다음을 한다.

1. `sql/reset.sql`: DB를 비우고 회원 2,000명(포인트 10,000,000)과 관리자를 넣는다. 비밀번호는 모두 `password1234`다.
2. `sql/waits.sql`: 측정하는 동안 0.2초마다 앱의 DB 연결 수와 행 잠금을 기다리는 연결 수를 센다.
3. k6 시나리오: setup에서 관리자 API로 회차와 좌석을 만들고 회원을 로그인시킨 뒤 부하를 건다.
4. `sql/check.sql`: 정합성 위반 건수를 센다.

## 시나리오

| 파일 | 상황 | 부하 |
| --- | --- | --- |
| `warmup.js` | 측정 전 JVM 워밍업 | 초당 예매 20건 × 30초 |
| `rush.js` | 티켓 오픈 순간. 좌석보다 사람이 많고 같은 좌석을 두고 경쟁한다 | 회원 500명이 좌석 200석에 동시에 몰린다. 남이 먼저 잡으면 좌석 배치를 다시 보고 다른 좌석을 고른다(최대 5번) |
| `hot.js` | 인기 좌석 쟁탈. 행 잠금이 실제로 부딪히게 한다 | 회원 300명이 좌석 60석에 몰리고, 한 명이 두 좌석을 무작위 순서로 한 번에 선점한다(최대 5번) |
| `steady.js` | 평소 부하. 회원마다 다른 좌석을 골라 경합이 없다 | 초당 예매 50건 × 60초 |

예매 한 건은 좌석 1석 선점 후 바로 결제다.

## 출력 읽는 법

```text
[rush] 2026-11-18T10:29:47.724Z
  예매   성공=200 포기=300 마지막 성공=5679ms 초당 예매=35.2
  선점   성공=200 좌석 선점 실패=588 그 밖의 실패=0  p50=930ms p95=1886ms p99=2713ms max=3396ms
  결제   성공=200 실패=0  p50=2045ms p95=2865ms p99=2925ms max=3431ms
  오류   5xx·연결 실패=0 놓친 반복=0
  DB 연결  표본=77 평균 사용=6.8 최대 사용=10 평균 잠금 대기=0.1 최대 잠금 대기=1
```

| 항목 | 뜻 |
| --- | --- |
| 포기 | 5번 시도해도 좌석을 못 잡았거나 결제에 실패한 회원 |
| 마지막 성공 | 시나리오 시작부터 마지막 예매가 끝날 때까지. rush에서는 매진까지 걸린 시간이다 |
| 좌석 선점 실패 | `409 SEAT_NOT_AVAILABLE`. 남이 먼저 잡은 좌석을 고른 횟수 |
| 그 밖의 실패 | 그 밖의 4xx·5xx. 0이 아니면 원인을 먼저 찾는다 |
| 놓친 반복 | 부하 도구가 정한 속도로 요청을 보내지 못한 횟수. 0이 아니면 측정 PC가 모자란 것이다 |
| DB 연결 | 앱 연결 중 일하는 연결 수와 행 잠금을 기다리는 연결 수. 준비 단계(로그인)의 표본도 섞인다 |

전체 결과는 `perf/results/`에 JSON으로 남는다(git에 올리지 않는다).

## 지킬 것

- `check.sql`의 `violations`가 하나라도 0이 아니면 그 측정은 버리고 원인을 찾는다. 빨라도 정합성이 깨지면 의미가 없다.
- 측정하는 동안 빌드, 영상 재생처럼 CPU를 많이 쓰는 프로그램을 끈다. 앱, DB, k6가 한 PC에서 CPU를 나눠 쓴다.
- 비교하는 두 측정은 같은 조건(장비, 데이터 양, 앱 설정, 워밍업)에서 한다.
