# 요구사항 정의

콘서트 좌석 예매 서비스의 기능 범위와 규칙을 정한다. 설계와 구현은 이 문서를 기준으로 하고, 범위나 규칙이 바뀌면 이 문서를 먼저 고친다.

## 1. 목적

인기 공연의 예매가 열리는 순간 같은 좌석에 요청이 몰려도 **한 좌석은 한 사람에게만 팔린다**. 이 정합성을 지키면서 몰리는 요청을 얼마나 버티는지 측정하고 개선하는 것이 이 프로젝트의 핵심이다.

## 2. 사용자

| 역할 | 하는 일 |
| --- | --- |
| 관람객 (`USER`) | 공연을 찾고, 좌석을 선점하고, 포인트로 결제하고, 예매를 취소한다 |
| 관리자 (`ADMIN`) | 공연과 회차를 등록하고 공개하며, 회차를 취소하면 예매자에게 일괄 환불한다 |

## 3. 용어

코드의 이름은 이 표를 따른다. 같은 개념을 다른 이름으로 부르지 않는다.

| 용어 | 코드 이름 | 뜻 |
| --- | --- | --- |
| 공연 | `Concert` | 제목·설명을 가진 공연 자체. 여러 회차를 가진다 |
| 회차 | `Performance` | 공연의 특정 날짜·시간·장소 한 번. 좌석과 예매 오픈 시각을 가진다 |
| 공연장 | `Venue` | 회차가 열리는 장소 |
| 좌석 등급 | `SeatGrade` | 회차별 등급 이름(VIP, R 등)과 가격 |
| 좌석 | `Seat` | 회차에 속한 좌석 하나. 등급을 가진다 |
| 선점 | `Hold` | 결제 전까지 좌석을 잠시 다른 사람이 못 사게 잡아 두는 것. 좌석의 `HELD` 상태와 결제 대기 예매로 나타난다 |
| 예매 | `Reservation` | 한 사용자가 한 회차에서 좌석을 사는 단위. 선점으로 시작해 결제로 확정된다 |
| 예매 좌석 | `ReservationSeat` | 예매에 포함된 좌석 하나와 선점 시점의 가격 |
| 결제 | `Payment` | 예매 금액을 포인트로 지불한 기록 |
| 환불 | `Refund` | 결제한 금액을 포인트로 되돌리는 것. 결제의 `REFUNDED` 상태와 포인트 거래로 남는다 |
| 포인트 | `Point` | 결제 수단. 사용자가 충전해서 쓴다 |
| 포인트 지갑 | `PointWallet` | 회원 한 명의 포인트 잔액 |
| 포인트 거래 | `PointTransaction` | 충전·결제·환불로 잔액이 바뀐 기록 하나 |

## 4. 기능 범위

### MVP (이번에 만든다)

**회원**
- 회원가입, 로그인(이메일·비밀번호), 로그아웃
- 포인트 충전, 포인트 내역 조회

**공연 조회**
- 공개된 공연 목록 (페이지네이션)
- 공연 상세와 회차 목록
- 회차의 등급별 잔여 좌석 수, 좌석 배치(좌석별 판매 가능 여부)

**예매**
- 좌석 선점: 한 번에 여러 좌석을 고를 수 있다. 하나라도 못 잡으면 전부 실패한다
- 선점 취소: 결제 전에 선점을 직접 풀 수 있다
- 결제: 선점한 좌석을 포인트로 결제해 예매를 확정한다
- 선점 만료: 시간 안에 결제하지 않으면 선점이 풀린다
- 예매 취소: 확정된 예매를 취소하고 환불받는다
- 내 예매 목록, 예매 상세

**관리자**
- 공연장 등록
- 공연 등록·수정·공개·종료
- 회차 등록 (등급별 가격·좌석 수로 좌석을 일괄 생성)
- 회차 취소 (해당 회차의 모든 예매를 취소하고 일괄 환불)
- 회차별 판매 현황 (판매 좌석 수, 매출)

### 이후 (MVP에서 제외)

| 기능 | 제외 이유 |
| --- | --- |
| 대기열 | MVP의 동시성 측정 결과를 보고 필요성을 판단한다 |
| 소셜 로그인 | 예매 핵심 흐름과 무관하다 |
| 실제 PG 결제 연동 | 포인트 결제로 결제 흐름과 보상 처리를 먼저 검증한다 |
| 알림 (메일·푸시) | 핵심 흐름과 무관하다 |
| 좌석 배치도 이미지, 검색·필터 | 화면 중심 기능이다 |

## 5. 업무 규칙

### 선점
- 예매 오픈 시각 전에는 선점할 수 없다.
- 공연 시작 시각이 지난 회차는 선점할 수 없다.
- 한 번에 선점할 수 있는 좌석 수는 최대 4석이다.
- 선점 유효 시간은 10분이다. 지나면 자동으로 풀린다.
- 한 사용자는 한 회차에 결제 대기 중인 예매를 하나만 가질 수 있다. 새로 고르려면 기존 선점을 먼저 취소한다.

### 결제
- 예매 금액은 선점할 때의 좌석 등급 가격을 합한 값이다. 그 뒤 가격이 바뀌어도 이 예매의 금액은 바뀌지 않는다.
- 결제와 환불은 예매 금액으로 한다.
- 포인트 잔액이 부족하면 결제할 수 없다. 잔액은 음수가 될 수 없다.
- 같은 결제 요청이 여러 번 와도 결제는 한 번만 된다.
- 선점이 만료된 예매는 결제할 수 없다.

### 취소·환불
- 관람객은 공연 시작 24시간 전까지 확정된 예매를 취소할 수 있다. 환불 금액은 결제 금액 전액이다.
- 취소한 좌석은 다시 판매 가능해진다.
- 관리자가 회차를 취소하면 시점과 관계없이 전액 환불한다. 그 회차의 좌석은 더 이상 팔지 않는다.

### 공연·회차
- 공연은 `준비 중 → 공개 → 종료` 순서로 바뀐다. 준비 중인 공연은 관람객에게 보이지 않는다.
- 회차가 하나 이상 있어야 공개할 수 있다.
- 예매 오픈 시각은 공연 시작 시각보다 앞서야 한다.

### 회원
- 결제 기록이 있는 회원이 탈퇴해도 결제·환불 기록은 지우지 않는다.
- 결제 대기 중이거나 확정된 예매가 있으면 탈퇴할 수 없다.
- 탈퇴한 회원의 이메일로 다시 가입할 수 있다.

## 6. 비기능 요구사항

| 항목 | 목표 | 확인 방법 |
| --- | --- | --- |
| 좌석 정합성 | 같은 좌석의 중복 선점·중복 판매 0건 | 동시 요청 테스트 |
| 금액 정합성 | 포인트 잔액, 결제 합계, 환불 합계가 항상 맞는다 | 동시 결제·환불 테스트 |
| 처리량 | 좌석 1,000석 회차에 동시 선점 요청 5,000건을 보낼 때 정합성을 지키고 서버 오류 0건 | 부하 테스트 (k6) |
| 응답 시간 | 선점 API p95 500ms 이하 | 부하 테스트 |
| 보안 | 본인의 예매·포인트만 조회·변경할 수 있다. 관리자 API는 관리자만 호출한다 | 인증·인가 테스트 |
| 실행 환경 | 저장소를 받은 사람이 명령 몇 개로 로컬에서 실행할 수 있다 | README 절차대로 실행 |

처리량과 응답 시간 목표는 첫 측정 전의 가정이다. 측정 결과를 보고 이 표를 고친다.

## 7. 제외 범위

- 프론트엔드 화면. API와 문서(Swagger)로 확인한다.
- 실제 결제, 실제 금전 거래.
- 운영 배포. 로컬 Docker 환경까지만 책임진다.
