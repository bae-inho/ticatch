# 0005. 시각은 timestamptz와 Instant로 다루고, API에서 한국 시간으로 바꾼다

- 상태: 채택
- 날짜: 2026-10-28

## 배경

이 서비스는 시각 비교가 핵심 규칙에 들어간다. 예매 오픈 시각, 선점 만료(10분), 환불 마감(공연 24시간 전)이 모두 "지금"과의 비교다. 시각이 서버나 DB 설정에 따라 다르게 해석되면 이 규칙이 조용히 틀린다.

이전 버전은 Java `LocalDateTime`과 MySQL `DATETIME`을 쓰고, JDBC URL의 `serverTimezone=Asia/Seoul`로 해석을 맞췄다. `LocalDateTime`은 "어느 지역의 몇 시인지"를 모르는 값이다. 서버의 기본 시간대가 바뀌면(클라우드 서버는 보통 UTC다) 같은 값이 9시간 다른 순간으로 해석된다.

## 결정

| 위치 | 타입 | 이유 |
| --- | --- | --- |
| DB | `timestamptz` | 저장할 때 UTC 기준의 한 순간으로 바꿔 저장한다. 접속한 세션의 시간대와 무관하다 |
| 엔티티·서비스 | `java.time.Instant` | 시간대 없이 "한 순간"만 나타낸다. 비교와 계산에 모호함이 없다 |
| API 요청·응답 | `OffsetDateTime` (`+09:00`) | 사람이 읽는 값은 한국 시간으로 보여 준다([API 설계 1절](../api.md#요청응답-형식)) |

- 요청으로 받은 `OffsetDateTime`은 컨트롤러에서 `Instant`로 바꿔 서비스에 넘긴다.
- 서비스가 돌려준 `Instant`는 응답 DTO에서 `Asia/Seoul` 기준 `OffsetDateTime`으로 바꾼다.
- "지금"은 `Instant.now()`를 직접 부르지 않고 주입받은 `Clock`에서 얻는다. 그래야 테스트에서 시각을 고정할 수 있다(4단계에서 구현한다).

## 검토한 대안

### `LocalDateTime` + `timestamp` (이전 방식)

국내 프로젝트에서 가장 흔하다. 서버와 DB가 모두 한국 시간으로 설정돼 있으면 문제가 드러나지 않는다. 하지만 그 설정이 하나라도 바뀌면 저장된 값 전체가 다른 순간을 가리킨다. 이 서비스처럼 시각 비교가 규칙의 핵심이면 그 위험을 질 이유가 없다.

### 엔티티에도 `OffsetDateTime`

값에 오프셋이 있어 모호함은 없다. 하지만 PostgreSQL은 오프셋을 저장하지 않고 UTC로 바꿔 저장하므로, 읽어 올 때 오프셋이 저장한 값과 달라진다(`+09:00`으로 넣고 `+00:00`으로 받는다). 같은 순간인데 `equals`가 `false`가 되는 혼란이 생긴다.

## 결과

얻는 것:

- 서버, DB, JVM의 시간대 설정과 무관하게 같은 순간을 가리킨다.
- 만료·마감 계산이 `Instant`끼리의 비교라 단순하다.

감수하는 것:

- 계층 경계(컨트롤러 ↔ 서비스)에서 `OffsetDateTime` ↔ `Instant` 변환 코드가 필요하다.
- DB를 직접 조회하면 세션 시간대 기준으로 보인다. 확인할 때 `SET TIME ZONE 'Asia/Seoul'`을 쓰면 편하다.
