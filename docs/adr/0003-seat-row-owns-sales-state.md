# 0003. 좌석의 판매 상태는 좌석 행이 가진다

- 상태: 채택
- 날짜: 2026-10-28

## 배경

"한 좌석은 동시에 한 예매에만 선점·판매된다"가 이 서비스의 가장 중요한 규칙이다. 이 규칙을 지키려면 먼저 "이 좌석이 지금 팔 수 있는가"라는 정보를 어디에 둘지 정해야 한다. 어디에 두느냐에 따라 동시성 제어 방식과 좌석 배치도 조회 방식이 달라진다.

## 결정

- 좌석 테이블의 `status` 컬럼(`AVAILABLE`, `HELD`, `SOLD`)이 판매 상태의 원본이다.
- 좌석 상태는 예매 상태를 바꾸는 트랜잭션 안에서 함께 바꾼다([도메인 설계 3절](../domain.md#3-사건별-상태-변화)).
- 선점은 전부 아니면 전무다. 요청한 좌석이 모두 `AVAILABLE`일 때만 모두 `HELD`로 바꾸고, 하나라도 아니면 트랜잭션 전체를 되돌린다.
- 여러 좌석을 잠글 때는 항상 좌석 ID 오름차순으로 잠가 교착 상태를 막는다.

같은 좌석을 동시에 바꾸는 요청을 어떻게 줄 세울지(조건부 갱신, 비관적 락, 낙관적 락, 분산 락)는 이 ADR에서 정하지 않는다. 이 구조를 기준선으로 두고 7단계에서 방식별로 측정해 정한다. 결과에 따라 판매 상태의 위치가 바뀌면 새 ADR로 이 결정을 대체한다.

## 검토한 대안

### 예매 좌석 테이블의 유일 인덱스로 판단

`RESERVATION_SEAT`에 예매 상태를 복사해 두고 `UNIQUE (seat_id) WHERE status IN ('PENDING', 'CONFIRMED')`를 건다. 중복 판매를 DB가 직접 막는다는 장점이 있다. 하지만 예매 상태를 두 테이블에 나눠 들고 있어야 하고, 좌석 배치도를 보여 줄 때마다 예매 좌석 테이블을 조인해야 한다.

### Redis에 선점 상태를 둠

선점 요청이 몰릴 때 DB 부하를 크게 줄일 수 있다. 하지만 Redis와 DB가 하나의 트랜잭션으로 묶이지 않아, 한쪽만 반영됐을 때 되돌리는 보상 로직이 필요하다. 측정으로 DB가 병목임을 확인하기 전에 도입하면 복잡도만 늘어난다.

## 결과

얻는 것:

- 좌석 배치도는 좌석 테이블 하나만 읽으면 된다.
- 판매 상태와 예매 상태가 같은 DB, 같은 트랜잭션에 있어 일관성을 지키기 쉽다.
- 이후 락 방식을 비교할 때 기준이 되는 단순한 구조다.

감수하는 것:

- 인기 좌석 행에 갱신이 몰린다. 이 경합이 얼마나 큰지가 7단계의 측정 대상이다.
- 좌석 상태와 예매 상태가 일치하는지는 DB 제약으로 표현할 수 없어 테스트로 지켜야 한다.
