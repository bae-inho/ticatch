# 0007. 인증은 JWT access token과 DB에 저장한 refresh token으로 한다

- 상태: 채택
- 날짜: 2026-11-04

## 배경

[API 설계](../api.md)에서 사용자를 `Authorization: Bearer` 헤더의 토큰으로만 식별하고, 로그인·재발급·로그아웃 API를 두기로 했다. 이제 토큰의 종류, 수명, 서버에 무엇을 저장할지, 어떻게 검증할지를 정해야 한다.

판단 기준은 셋이다.

1. 예매가 몰릴 때 인증이 병목이 되지 않아야 한다. 요청마다 DB나 별도 저장소를 조회하는 방식은 부하 측정(7단계) 결과를 흐린다.
2. 로그아웃하면 그 로그인을 더는 이어 갈 수 없어야 한다.
3. 보안 코드를 직접 짜는 양을 줄인다. 직접 만든 검증 코드는 실수할 곳이 많다.

## 결정

| 토큰 | 형식 | 수명 | 서버 저장 |
| --- | --- | --- | --- |
| access token | JWT, HS256 서명. `sub`에 회원 ID, `role`에 역할 | 30분 | 저장하지 않는다 |
| refresh token | 32바이트 난수 | 14일 | SHA-256 해시를 `refresh_token` 테이블에 저장한다 |

- **access token 검증은 스프링 시큐리티의 Resource Server 기능에 맡긴다.** 서명, 만료, 역할(`ROLE_USER`, `ROLE_ADMIN`) 변환을 직접 구현하지 않는다. 서버는 세션을 만들지 않는다(STATELESS).
- **refresh token은 한 번 쓰면 지운다(회전).** 재발급할 때마다 새 refresh token을 준다. 같은 토큰으로 동시에 두 번 재발급하면, DB의 DELETE가 지운 행 수로 한 요청만 성공시킨다.
- **refresh token 원문은 저장하지 않는다.** DB가 유출돼도 해시로는 재발급을 받을 수 없다. 추측할 수 없는 난수라 비밀번호처럼 느린 해시(BCrypt)를 쓸 필요는 없다.
- **로그아웃은 그 기기의 refresh token을 지운다.** 이미 발급한 access token은 남은 수명 동안 유효하다.
- **비밀번호는 BCrypt로 해시한다.** 저장값에 `{bcrypt}`처럼 알고리즘 이름을 붙여, 나중에 알고리즘을 바꿔도 기존 비밀번호를 검증할 수 있게 한다.
- **401을 만료와 위조로 나누지 않는다.** API 설계에서 `TOKEN_EXPIRED`를 따로 두려 했지만 뺐다. 이유는 아래 대안에 있다.
- 401·403도 다른 에러와 같은 Problem Details 형식으로 보낸다. 보안 필터의 예외를 스프링 MVC 예외 처리기로 넘긴다([ADR 0006](0006-business-errors-use-one-exception-and-module-error-codes.md)).

## 검토한 대안

### 서버 세션 (쿠키 + 세션 저장소)

로그아웃이 즉시 반영되고 구현이 단순하다. 웹 화면만 있는 서비스라면 오히려 더 나은 선택이다. 하지만 요청마다 세션 저장소를 조회해야 하고, 서버를 여러 대 띄우면 세션 저장소(Redis 등)가 따로 필요하다. 이 프로젝트는 화면이 없는 API 서버이고 부하 측정이 핵심이라, 인증이 저장소를 거치지 않는 쪽을 골랐다.

### refresh token도 JWT로 만들고 저장하지 않음

서버가 아무것도 저장하지 않아 가장 단순하다. 하지만 발급한 토큰을 무효로 만들 방법이 없어 로그아웃이 의미가 없다. 탈취된 토큰도 14일 동안 쓸 수 있다.

### refresh token을 Redis에 저장

조회가 빠르고 만료(TTL)를 Redis가 알아서 처리한다. 하지만 아직 Redis를 쓰지 않는다. refresh token은 로그인과 재발급 때만 읽으므로 DB로 충분하다.

### JWT 필터를 직접 구현 (jjwt 등)

국내 자료에서 흔한 방식이다. 토큰 파싱, 서명·만료 검증, 예외 처리, 인증 객체 생성을 모두 직접 짜야 한다. 스프링 시큐리티가 같은 기능을 표준으로 제공하므로 직접 짤 이유가 없다.

### 만료(`TOKEN_EXPIRED`)와 위조(`UNAUTHORIZED`)를 다른 코드로 응답

클라이언트가 만료일 때만 재발급을 시도할 수 있다. 하지만 스프링 시큐리티는 둘을 같은 예외로 알려 주고, 둘을 가르려면 예외 메시지 문자열을 비교하거나 검증기를 따로 만들어야 한다. 클라이언트도 "401이면 재발급을 한 번 시도하고, 그것도 실패하면 로그인"이라는 규칙 하나로 충분하다. 그래서 401은 `UNAUTHORIZED` 하나로 둔다.

## 결과

얻는 것:

- API 요청 대부분이 DB 조회 없이 인증된다. 서버를 여러 대로 늘려도 인증을 위해 공유할 상태가 없다.
- 로그아웃과 refresh token 탈취에 대응할 수 있다. 회전 덕분에 탈취된 refresh token은 정상 사용자가 먼저 쓰면 무효가 된다.
- 보안 검증 코드를 직접 짜지 않는다.

감수하는 것:

- 로그아웃하거나 탈퇴해도 access token은 최대 30분 동안 유효하다.
- 서명 키(`JWT_SECRET`)가 유출되면 누구나 토큰을 만들 수 있다. 서버에 띄울 때는 반드시 환경 변수로 기본값과 다른 키를 넣어야 한다.
- 로그인할 때마다 refresh token 행이 생긴다. 로그아웃하지 않고 만료된 행을 지우는 정리 작업은 아직 없다.
