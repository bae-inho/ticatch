# 0004. 성공 응답은 감싸지 않고, 에러는 Problem Details로 보낸다

- 상태: 채택
- 날짜: 2026-10-28

## 배경

이전 버전은 모든 응답을 `ApiResponse { status, message, data }`로 감쌌다. 그 결과 세 가지 문제가 있었다.

1. **HTTP 상태와 본문이 어긋났다.** 낙관적 락 충돌과 DB 제약 위반 핸들러가 `200 OK`에 `"status": "ERROR"` 본문을 보냈다. 상태 코드만 보는 클라이언트, 모니터링, 로드밸런서는 이를 성공으로 셌다.
2. **에러 종류를 구분할 수 없었다.** 업무 에러는 모두 `400`과 한국어 메시지뿐이었다. 클라이언트가 "좌석이 이미 팔림"과 "잔액 부족"을 구분하려면 메시지 문자열을 비교해야 했다.
3. **같은 정보를 두 번 보냈다.** 성공·실패 여부가 HTTP 상태 코드와 본문의 `status`에 중복으로 들어 있었다.

## 결정

- **성공 응답**은 결과 객체를 그대로 본문으로 보낸다. 성공 여부는 HTTP 상태 코드(2xx)로만 나타낸다.
- **에러 응답**은 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) 형식(`application/problem+json`)으로 보낸다. 표준 필드(`type`, `title`, `status`, `detail`, `instance`)에 확장 필드 `code`를 더한다.
- `code`는 에러 종류를 나타내는 고정 문자열이다. 클라이언트는 `code`로 분기하고, `detail`은 사용자에게 보여 주는 문구로만 쓴다.
- 에러 응답의 HTTP 상태는 항상 4xx 또는 5xx다.

형식과 에러 코드 목록은 [API 설계 2절](../api.md#2-에러-응답)에 있다.

## 검토한 대안

### 공통 봉투 `{ success, data, error }`

국내 실무에서 많이 쓰는 방식이다. 모든 응답이 같은 모양이라 클라이언트의 파싱 코드가 단순해진다는 장점이 있다. 하지만 HTTP 상태와 본문의 성공 여부가 따로 놀 수 있고, 실제로 이전 버전에서 그런 버그가 났다. 봉투를 쓰더라도 HTTP 상태를 정확히 지켜야 한다면, 봉투가 주는 이점은 "모양이 같다"는 것뿐이다.

### 팀 자체 에러 형식 `{ code, message, errors }`

단순하고 흔하다. Problem Details와 정보는 거의 같지만 표준이 아니다. Spring Boot가 `ProblemDetail`을 기본 지원하므로, 자체 형식을 따로 만들 이유가 약하다.

## 결과

얻는 것:

- HTTP 상태 코드만으로 성공·실패, 에러 분류(400·404·409)가 정확히 드러난다.
- Spring의 `ProblemDetail`, `ErrorResponseException`과 표준 예외 처리를 그대로 활용할 수 있다.
- 클라이언트가 문구가 아니라 `code`로 분기하므로, 문구를 바꿔도 클라이언트가 깨지지 않는다.

감수하는 것:

- 성공 응답의 모양이 API마다 다르다. 공통 처리가 필요하면 클라이언트가 상태 코드로 먼저 분기해야 한다.
- 국내 실무 프로젝트 중 공통 봉투를 쓰는 곳과는 형식이 다르다. 면접에서 선택 이유를 설명할 수 있어야 한다.
