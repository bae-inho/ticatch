# 0008. 좌석 선점의 기준선은 ID 순서로 잡는 비관적 락이다

- 상태: 채택
- 날짜: 2026-11-04

## 배경

[ADR 0003](0003-seat-row-owns-sales-state.md)에서 좌석의 판매 상태는 좌석 행이 갖기로 했고, 같은 좌석을 동시에 바꾸는 요청을 어떻게 줄 세울지는 7단계에서 측정해 정하기로 미뤘다. 하지만 측정하려면 비교할 기준선이 먼저 있어야 하고, 기능은 그 전에 올바르게 동작해야 한다.

기준선은 세 조건을 만족해야 한다.

1. 같은 좌석은 한 명만 선점한다(경합 지점 1).
2. 여러 좌석을 서로 다른 순서로 고른 요청끼리 교착 상태에 빠지지 않는다(경합 지점 2).
3. 선점은 전부 아니면 전무다. 하나라도 못 잡으면 아무것도 잡지 않는다.

## 결정

- 요청한 좌석을 `SELECT ... WHERE performance_id = ? AND id IN (...) ORDER BY id FOR UPDATE`로 잠그고 읽는다. 상태 확인과 변경은 잠근 뒤에 한다.
- **잠그는 순서는 항상 좌석 ID 오름차순이다.** A가 1→2, B가 2→1 순서로 잠그면 서로가 잡은 행을 기다리는 교착 상태가 생긴다. 모두 같은 순서로 잠그면 생기지 않는다. 쿼리 실행 계획에 기대지 않고 `ORDER BY`로 순서를 명시한다.
- 하나라도 선점·판매된 좌석이면 예외를 던져 트랜잭션 전체를 되돌린다.
- 회원·회차당 결제 대기 예매가 하나라는 규칙(경합 지점 3)은 좌석 락이 아니라 조건부 유일 인덱스가 지킨다.

## 검토한 대안

7단계에서 아래 방식들을 이 기준선과 같은 조건으로 측정해 비교한다.

| 방식 | 예상 장점 | 예상 단점 |
| --- | --- | --- |
| 조건부 UPDATE (`UPDATE seat SET status='HELD' WHERE id IN (...) AND status='AVAILABLE'`, 바뀐 행 수 확인) | 읽고 쓰는 왕복이 한 번이라 빠르다 | 여러 행을 한 문장으로 바꿀 때 잠금 순서를 문장 안에서 보장하기 어렵다 |
| 낙관적 락 (`@Version`) | 충돌이 드물면 대기 없이 빠르다 | 인기 좌석처럼 충돌이 잦으면 실패와 재시도가 폭증한다 |
| Redis 분산 락·선점 | DB 부하를 줄인다 | Redis와 DB가 한 트랜잭션이 아니라 보상 처리가 필요하다 |

## 결과

얻는 것:

- 동시성 테스트(`ReservationConcurrencyTest`)로 세 조건을 확인한다. 20명이 같은 좌석을 동시에 선점하면 한 명만 성공한다.
- 잠금을 빼면 같은 테스트에서 20명 중 10명이 같은 좌석을 "선점"했다. 이 락이 실제로 이중 판매를 막고 있다는 근거다.

감수하는 것:

- 인기 좌석에 요청이 몰리면 요청들이 그 행의 잠금을 기다리며 DB 커넥션을 쥐고 있는다. 이 대기가 얼마나 처리량을 떨어뜨리는지가 7단계의 측정 대상이다.
