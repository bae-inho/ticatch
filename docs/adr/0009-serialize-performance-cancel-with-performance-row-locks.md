# 0009. 회차 취소는 회차 행 잠금으로 선점·환불과 줄 세운다

- 상태: 채택
- 날짜: 2026-11-05

## 배경

회차 취소는 회차 상태와 그 회차의 예매·좌석·결제·지갑을 한 번에 바꾼다(경합 지점 8). 같은 회차의 선점·결제·환불이 동시에 들어오면 두 가지가 깨진다.

1. **취소된 회차에 예매가 남는다.** 회차 취소가 예매를 훑은 뒤 커밋하기 전에 선점이 들어오면, 선점은 회차를 아직 판매 중으로 읽고 새 결제 대기 예매를 만든다. 회차 취소는 이 예매를 보지 못했으므로, 취소가 끝난 뒤에도 취소된 회차에 `PENDING` 예매와 `HELD` 좌석이 남는다.
2. **교착 상태가 생긴다.** 환불은 결제 → 예매 순서로 잠근다. 회차 취소는 예매를 먼저 잠가 취소한 뒤 결제를 환불하므로 반대 순서다. 환불이 결제를, 회차 취소가 예매를 쥐고 서로를 기다린다.

## 결정

- **회차 취소는 회차 행을 배타 잠금(`SELECT ... FOR UPDATE`)으로 먼저 잡는다.** 그 뒤 예매(ID 순) → 좌석 → 결제 → 지갑(회원 ID 순) 순서로 바꾸고, 모두 한 트랜잭션으로 커밋한다.
- **선점과 환불은 회차 행을 공유 잠금(`SELECT ... FOR SHARE`)으로 먼저 잡는다.** 공유 잠금끼리는 서로 막지 않아 평소의 선점·환불은 서로를 기다리지 않는다. 회차 취소와는 서로를 기다린다.
  - 선점은 회차 취소가 끝날 때까지 기다린 뒤 취소된 회차를 읽고 `PERFORMANCE_NOT_ON_SALE`로 실패한다. 1번 문제가 사라진다.
  - 환불은 결제 행보다 회차 행을 먼저 잡으므로, 회차 취소와 결제·예매 잠금 순서가 엇갈리는 일이 생기지 않는다. 2번 문제가 사라진다.
- **결제, 선점 취소, 만료는 회차 행을 잠그지 않는다.** 셋 다 새 예매를 만들지 않고, 예매보다 결제 행을 먼저 잠그지도 않는다. 회차 취소가 어떤 예매의 잠금을 기다리는 동안 결제가 그 예매를 확정하고 커밋하면, 회차 취소는 확정된 예매를 읽고 방금 생긴 결제까지 환불한다.
- 회차 취소는 결제 행을 따로 잠그지 않는다. 회차 배타 잠금을 쥔 동안 그 회차의 결제를 바꿀 수 있는 환불은 회차 잠금에서 기다리고 있다.
- 회차 취소는 지갑을 회원 ID 순서로 잠근다. 회차 취소 두 건이 동시에 돌 때 같은 회원들의 지갑을 서로 다른 순서로 잠그지 않게 한다.
- 환불은 잠그기 전에 결제 엔티티를 읽지 않고 예매 ID만 읽는다. 엔티티를 먼저 읽어 두면 Hibernate가 잠금 조회 결과 대신 영속성 컨텍스트에 있던 이전 상태를 돌려준다.

## 검토한 대안

| 방식 | 고르지 않은 이유 |
| --- | --- |
| 선점·환불에서 회차 상태를 잠금 없이 확인 | 확인과 예매 생성 사이에 회차 취소가 끼어드는 1번 문제를 막지 못한다. 실제로 재현됐다(아래 결과) |
| 회차 취소도 결제 → 예매 순서로 잠금 | 환불과의 교착은 피하지만, 그 사이 새로 생기는 결제 대기 예매(1번)는 여전히 막지 못한다 |
| 결제에도 회차 공유 잠금 | 처음에는 넣었다. 위 이유로 필요 없고, 잠금을 빼고 동시성 테스트를 30회 반복해도 모두 통과했다. 인기 회차 행에 거는 공유 잠금을 늘리지 않으려고 뺐다 |
| 회차 행에 낙관적 락(`@Version`) | 선점이 충돌을 감지하려면 선점마다 회차 버전을 올려야(쓰기) 해서, 같은 회차의 선점끼리 서로 충돌한다 |
| 회차 상태만 먼저 커밋하고 예매 취소·환불은 나눠서 나중에 처리 | 예매 수와 관계없이 요청이 빨리 끝나지만, 실패를 다시 시도하는 장치와 진행 상태 조회가 필요하고 잠금 순서도 다시 설계해야 한다. 기준선은 한 트랜잭션으로 두고, 측정에서 예매가 많으면 느리다는 것을 확인해 7단계에서 이 방식과 비교한다([도메인 설계 7절](../domain.md#7-받아들인-한계)) |

## 결과

얻는 것:

- `PerformanceCancelConcurrencyTest`에서 회차 취소, 환불 2건, 결제 2건, 선점 1건을 동시에 출발시킨다. 교착 상태 없이 모든 예매가 취소되고, 모든 결제가 환불되고, 모든 회원의 잔액이 처음으로 돌아온다. 30회 반복해도 모두 통과했다.
- 잠금을 빼면 같은 테스트가 실패한다. 환불의 회차 잠금을 빼면 10회 중 4회 `deadlock detected`가 났다. 선점의 회차 잠금을 빼면 10회 중 7회 취소된 회차에 `PENDING` 예매가 남았다.

감수하는 것:

- 모든 선점이 회차 행 하나에 공유 잠금을 건다. PostgreSQL은 여러 트랜잭션이 같은 행을 공유 잠금하면 그 정보를 별도 구조(MultiXact)에 기록해 비용이 든다. 인기 회차에서 이 비용이 처리량을 얼마나 떨어뜨리는지 7단계에서 측정한다.
- 회차 취소가 진행되는 동안 그 회차의 선점·환불은 DB 커넥션을 쥐고 기다린다. 취소될 회차라 어차피 실패할 요청이지만, 취소가 길어지면 커넥션 풀을 차지한다. 로컬 측정에서 확정 예매 1,000건의 회차 취소에 14초가 걸렸다([도메인 설계 7절](../domain.md#7-받아들인-한계)).
