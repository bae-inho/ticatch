# 0010. 좌석 선점은 ID 순서 비관적 락을 유지한다

- 상태: 채택
- 날짜: 2026-11-18

## 배경

[ADR 0008](0008-hold-seats-with-ordered-pessimistic-locks.md)에서 좌석 선점의 기준선을 ID 순서로 잡는 비관적 락으로 정하고, 다른 방식과는 7단계에서 측정해 비교하기로 했다. Redis는 DB와 한 트랜잭션으로 묶을 수 없어 되돌리는 처리가 따로 필요하므로 이번 비교에서 뺐다.

비교한 방식은 넷이다. 네 방식 모두 전체 테스트 90개(동시 선점 테스트 포함)를 통과한 뒤 측정했다.

| 방식 | 구현 | 실험 브랜치 |
| --- | --- | --- |
| 비관적 락 (기준선) | 좌석을 `ORDER BY id`로 잠그고 읽은 뒤 상태 확인 | `test/seat-hold-comparison` `6d465ce` |
| NOWAIT | 기준선과 같지만 잠긴 좌석이 있으면 기다리지 않고 바로 실패 | `refactor/seat-hold-nowait` `009e76c` |
| 조건부 UPDATE | `UPDATE seat SET status = 'HELD' WHERE ... AND status = 'AVAILABLE'` 한 문장, 바뀐 행 수로 판단 | `refactor/seat-hold-conditional-update` `ec07157` |
| 낙관적 락 | 잠그지 않고 읽고, 저장할 때 `@Version`으로 충돌 확인 | `refactor/seat-hold-optimistic` `51e167d` |

측정 조건과 수치는 [성능 측정 기록 4절](../performance.md#4-좌석-선점-방식-비교-2026-11-18)에 있다. 시나리오는 두 가지다. 티켓 오픈(`rush.js`)은 회원 500명이 좌석 200석에 1석씩 몰린다. 인기 좌석(`hot.js`)은 회원 300명이 좌석 60석에 2석씩 몰린다. 커넥션 풀 10개(기본값)와 30개에서 쟀다.

## 결정

**기준선(ID 순서 비관적 락)을 그대로 쓴다.** 커넥션 풀도 기본값 10개를 유지한다.

## 검토한 대안

| 방식 | 측정 결과 | 고르지 않은 이유 |
| --- | --- | --- |
| NOWAIT | 인기 좌석·풀 10개에서 두 번 다 기준선보다 빨랐다. 매진 1.6초 대 2.4초, 교차 측정에서 3.4초 대 3.8초 | 이득이 극단적 경합에서만 나오고, 크기가 측정마다 크게 달라 확정하기 어렵다. 그리고 결국 실패할 트랜잭션(예: 두 좌석 중 하나가 이미 팔림)이 잠깐 잡은 좌석까지 "이미 선점됨"으로 응답한다. 사용자는 빈 좌석을 놓치고 다시 시도해야 한다 |
| 조건부 UPDATE | 모든 조건에서 기준선과 차이가 측정 흔들림 안이었다 | 이득이 없는데, 좌석 상태 규칙이 엔티티 메서드(`Seat.hold()`)에서 SQL로 빠져나간다. 여러 행을 한 문장으로 바꿀 때 잠그는 순서를 실행 계획에 맡긴다 |
| 낙관적 락 | 차이가 흔들림 안이었다. 충돌하면 앞 트랜잭션의 행 잠금을 기다린 뒤 실패해, 대기는 줄지 않았다 | 이득이 없는데 버전 열과 마이그레이션이 늘어난다 |
| 커넥션 풀 30개 | 네 방식 모두 풀 10개보다 빠르지 않았다. 행 잠금 대기는 늘었지만(최대 13~19개), 잠금 대기가 없는 NOWAIT도 똑같이 느려졌다 | 앱, DB, k6가 CPU 8개를 나눠 쓰는 환경이라 동시 실행만 늘고 처리량은 늘지 않았다 |

## 결과

얻는 것:

- 선점 코드가 바뀌지 않는다. 좌석 상태 규칙은 계속 `Seat` 엔티티가 지키고, 잠금 순서는 `ORDER BY id`가 보장한다.
- 같은 조건의 46번 측정 모두 정합성 위반이 0건이었다. 네 방식 모두 이중 선점·판매를 막는다는 것도 확인했다.
- 티켓 오픈의 지연은 잠금이 아니라 커넥션과 CPU를 기다리는 시간이라는 것을 확인했다(성능 측정 기록 3·4절).

감수하는 것:

- 같은 좌석에 요청이 몰리면 뒤 요청은 앞 트랜잭션이 끝날 때까지 커넥션을 쥐고 기다린다. 인기 좌석 경합에서 NOWAIT보다 느릴 수 있다.
- 측정은 노트북 한 대에서 했고, 같은 설정을 다시 재도 매진 시간이 2.4초에서 3.8초까지 흔들렸다. 운영과 비슷한 분리된 환경에서 인기 좌석 경합 때 NOWAIT의 이득이 이 흔들림보다 크게 나오면 다시 검토한다.

참고: Hibernate는 PostgreSQL에서 `PESSIMISTIC_WRITE`를 `FOR UPDATE`가 아니라 `FOR NO KEY UPDATE`로 보낸다. 외래 키 확인용 잠금(`FOR KEY SHARE`)과 부딪히지 않는 더 약한 배타 잠금이고, 좌석 행끼리는 `FOR UPDATE`와 똑같이 서로를 막는다.
