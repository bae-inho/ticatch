# 0011. 회차 취소는 한 트랜잭션에서 테이블마다 한 문장으로 바꾼다

- 상태: 채택
- 날짜: 2026-11-18

## 배경

[ADR 0009](0009-serialize-performance-cancel-with-performance-row-locks.md)의 회차 취소는 회차, 예매, 좌석, 결제, 포인트를 한 트랜잭션으로 바꾼다. 예매를 한 건씩 엔티티로 읽고 바꿔서, 예매 한 건마다 SQL을 8개 보냈다.

7단계에서 확정 예매 N건으로 매진된 회차를 취소해 보니 두 가지 문제가 드러났다([성능 측정 기록 5절](../performance.md#5-회차-취소-개선-2026-11-18)).

1. **느리다.** 1,000건에 21초, 4,000건에 143초가 걸렸다. 회차 하나에 좌석은 최대 50,000석이라 예매도 최대 50,000건이다.
2. **앱 전체가 멈춘다.** 취소 트랜잭션은 환불하면서 잠근 회원 지갑을 커밋할 때까지 쥐고 있다. 그 회원들의 충전 요청이 지갑 잠금을 기다리며 DB 커넥션(최대 10개)을 하나씩 차지한다. 풀이 차면 관계없는 공연 목록 조회도 커넥션을 기다린다. 4,000건 취소 중에는 공연 목록 조회 p95가 47초였고, 커넥션을 30초 안에 받지 못한 요청 77건이 실패했다.

목표를 두 가지로 정했다. 최대 규모(50,000건)도 HTTP 시간 제한(보통 30초) 안에 넉넉히 끝낸다. 취소하는 동안 관계없는 요청이 느려지지 않는다.

## 결정

- **회차 취소는 계속 한 트랜잭션이다.** 회차 행 잠금(ADR 0009)도 그대로다.
- **예매, 좌석, 결제는 테이블마다 UPDATE 한 문장으로 바꾼다.** 엔티티를 읽지 않는다.
  - 예매: 그 회차의 `PENDING`·`CONFIRMED`를 `CANCELED`로
  - 좌석: 그 회차의 `HELD`·`SOLD`를 `AVAILABLE`로. 좌석 상태와 예매 상태는 늘 일치하므로(불변식 10) 방금 취소한 예매의 좌석과 같다
  - 결제: 그 회차의 `PAID`를 `REFUNDED`로. 지갑 환불에 필요한 결제 ID, 회원 ID, 금액만 먼저 읽는다
- **지갑은 회원 ID 순서로 1,000명씩 묶어 잠그고, 환불 거래는 JDBC 배치로 넣는다.** 잔액 변경은 엔티티로 하고, UPDATE를 100개씩 묶어 보낸다(`hibernate.jdbc.batch_size`).

## 검토한 대안

| 방식 | 확정 예매 50,000건 | 고르지 않은 이유 |
| --- | --- | --- |
| 기존 (한 건씩 엔티티로) | 재지 않음. 4,000건에 143초 | 느리고, 취소하는 동안 앱 전체가 멈춘다 |
| 묶어 보내기: 엔티티는 그대로 읽고, 좌석은 회차 단위로 한 번에 읽고, UPDATE를 묶어 보냄 | 16.5초. 그동안 공연 목록 p95 4.8초 | 목표 시간은 넘지 않지만 3배 느리다. 예매·좌석·결제 엔티티를 15만 개 메모리에 올리고, 지갑을 잠근 뒤 커밋까지가 길어 관계없는 요청이 몇 초씩 기다린다 |
| 나눠서 비동기로 처리: 회차 상태만 먼저 커밋하고 예매는 스케줄러가 조금씩 취소 | 재지 않음 | 한 트랜잭션으로도 최대 규모가 5초에 끝나 필요하지 않다. 실패를 다시 시도하는 장치, 진행 상태 조회, 잠금 순서 재설계가 필요하고, 그사이 결제가 취소된 회차를 확정하지 못하게 막는 검사도 더해야 한다 |

묶어 보내기 구현은 실험 브랜치 `refactor/cancel-batched`(`1e18fdc`)에 남겼다.

## 결과

얻는 것:

- 확정 예매 1,000건 21.4초 → 0.26초, 4,000건 143.1초 → 0.62초, 최대 규모 50,000건 5.0초.
- 50,000건을 취소하는 동안에도 관계없는 공연 목록 조회 p95가 61ms였다. 실패한 요청은 없었다.
- 33번 측정 모두 정합성 위반 0건. 회차 취소 동시성 테스트(`PerformanceCancelConcurrencyTest`)를 20번 반복해 교착 상태가 없음을 확인했다.

감수하는 것:

- **상태 전이 규칙이 두 곳에 있다.** 예매 취소, 좌석 되돌리기, 결제 환불의 "어떤 상태에서 어떤 상태로"를 엔티티 메서드(`Reservation.cancel()`, `Seat.release()`, `Payment.refund()` 등)와 UPDATE 문의 조건이 각각 갖는다. 회차 취소 API 테스트와 동시성 테스트가 두 쪽이 같은 결과를 내는지 지킨다.
- **예매를 ID 순서로 잠그지 않는다.** UPDATE는 행을 읽는 순서대로 잠근다. 그래도 교착이 생기지 않는다. 회차 배타 잠금을 쥔 동안 이 회차의 예매를 함께 잠글 수 있는 것은 예매 한 건만 잠그는 결제, 선점 취소, 만료뿐이다. 이들은 자기 예매를 잡은 뒤에는 그 예매의 좌석과 자기 지갑만 기다린다. 회차 취소는 예매를 모두 잡기 전에는 좌석과 지갑을 잠그지 않으므로, 서로를 기다리는 고리가 생기지 않는다.
- UPDATE 문은 영속성 컨텍스트를 거치지 않는다. 같은 트랜잭션에서 이 예매·좌석·결제를 미리 엔티티로 읽으면 옛 상태가 남는다. 지금 회차 취소는 회차 엔티티만 먼저 읽는다.
- 50,000건 취소에서 지갑을 잠근 뒤 커밋까지 그 회원들의 충전이 최대 2.4초 기다렸다.
