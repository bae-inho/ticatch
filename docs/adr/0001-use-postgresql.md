# 0001. 데이터베이스로 PostgreSQL을 쓴다

- 상태: 채택
- 날짜: 2026-10-28

## 배경

이전 버전은 MySQL 8을 썼다. 새로 시작하면서 MySQL을 유지할지, PostgreSQL로 바꿀지 정해야 했다.

판단 기준은 셋이다.

1. 예매 규칙을 DB 제약으로 지킬 수 있는가
2. 동시성 제어에 필요한 기능이 있는가
3. 실무와 채용 시장에서 통하는가

## 결정

PostgreSQL 17을 쓴다. 로컬과 테스트 모두 Docker로 같은 버전을 띄운다.

## 검토한 대안

### MySQL 8 유지

- 국내 실무 사용 비율은 여전히 MySQL이 높다. 대기업 레거시와 채용 공고에서 자주 보인다.
- 선점 중인 행 건너뛰기(`FOR UPDATE SKIP LOCKED`), 비관적 락, 낙관적 락은 MySQL 8에도 있다.
- 하지만 **조건부 유일 인덱스(partial unique index)가 없다.** "한 사용자는 한 회차에 결제 대기 예매를 하나만 가진다" 같은 규칙을 DB가 직접 지키게 하려면 계산 컬럼이나 별도 테이블을 써야 한다.

## 결과

얻는 것:

- **조건부 유일 인덱스**: `WHERE status = 'PENDING'` 조건이 붙은 유일 인덱스로, 같은 사용자의 중복 결제 대기 예매를 애플리케이션 락 없이 DB가 막는다.
- **CHECK 제약**: 포인트 잔액 `>= 0` 같은 규칙을 DB가 강제한다. MySQL도 8.0.16부터 지원하지만, PostgreSQL은 오래전부터 안정적으로 지원해 왔다.
- **트렌드**: Stack Overflow 개발자 설문에서 PostgreSQL이 가장 많이 쓰는 DB 1위를 이어 가고 있고, 국내 신규 서비스와 스타트업에서도 채택이 늘고 있다.

감수하는 것:

- 국내 레거시 실무와는 차이가 있다. 다만 JPA를 쓰므로 애플리케이션 코드 대부분은 DB와 무관하고, 락·인덱스·트랜잭션 격리 수준 같은 개념은 두 DB에서 공통이다.
- 기본 트랜잭션 격리 수준이 다르다. MySQL은 `REPEATABLE READ`, PostgreSQL은 `READ COMMITTED`다. 동시성 설계와 테스트는 PostgreSQL 기준으로 한다.
