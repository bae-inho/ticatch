# 성능 측정 기록

7단계에서 측정한 결과를 남긴다. 측정 방법과 실행 순서는 [perf/README.md](../perf/README.md)에 있다.

## 1. 측정 환경

앱, DB, 부하 도구(k6)가 노트북 한 대에서 CPU를 나눠 쓴다. 그래서 **절대 수치는 운영 환경을 뜻하지 않는다.** 같은 조건에서 방식끼리 비교하는 데만 쓴다.

| 항목 | 값 |
| --- | --- |
| 장비 | AMD Ryzen 7 4700U (8코어 8스레드), RAM 14GB, Windows 11 |
| Docker | Docker Desktop 29.7.2. VM에 CPU 8개, 메모리 6.7GB |
| DB | PostgreSQL 17.11 (Docker 컨테이너) |
| 앱 | Spring Boot 4.1.2, JDK 25 (Temurin), `java -jar`로 PC에서 직접 실행 |
| 앱 설정 | 기본값 그대로. DB 커넥션 풀(HikariCP) 최대 10개, 요청 스레드(Tomcat) 최대 200개 |
| 부하 도구 | k6 1.3.0 (Docker 이미지 `grafana/k6:1.3.0`) |

## 2. 측정 규칙

- 앱을 띄운 뒤 워밍업(`warmup.js`)을 한 번 돌리고 측정한다.
- 측정마다 DB를 같은 데이터로 되돌린다(`reset.sql`).
- 시나리오마다 3번 돌려 항목별 중앙값을 쓴다. 범위도 함께 적는다.
- 측정이 끝날 때마다 정합성을 확인한다(`check.sql`). 위반이 하나라도 있으면 그 측정은 쓰지 않는다.

## 3. 기준선 (2026-11-18)

좌석은 ID 순서로 잡는 비관적 락([ADR 0008](adr/0008-hold-seats-with-ordered-pessimistic-locks.md)), 선점 전에 회차 공유 잠금([ADR 0009](adr/0009-serialize-performance-cancel-with-performance-row-locks.md))을 거는 지금 구현이다. 6번 측정 모두 정합성 위반은 0건이었다.

### 티켓 오픈 (`rush.js`): 회원 500명, 좌석 200석

| 항목 | 중앙값 | 범위 (3회) |
| --- | --- | --- |
| 매진까지 걸린 시간 | 4.9초 | 3.8 ~ 5.1초 |
| 초당 예매 | 41.2건 | 38.9 ~ 52.4건 |
| 선점 응답 p50 / p95 / p99 | 1,047 / 1,541 / 1,677ms | p95 1,226 ~ 1,565ms |
| 결제 응답 p50 / p95 / p99 | 1,509 / 1,588 / 2,048ms | p95 1,339 ~ 2,397ms |
| 남이 먼저 잡은 좌석을 고른 횟수 | 616회 | 606 ~ 620회 |
| 행 잠금을 기다리는 DB 연결 (평균 / 최대) | 0.0 / 1개 | 최대 0 ~ 2개 |

200석이 모두 팔렸고, 남은 300명은 5번 시도 뒤 포기했다. 5xx와 연결 실패는 없었다.

### 평소 부하 (`steady.js`): 초당 예매 50건 × 60초, 좌석 경합 없음

| 항목 | 중앙값 | 범위 (3회) |
| --- | --- | --- |
| 처리한 예매 | 초당 50건 (목표 그대로, 놓친 반복 0) | |
| 선점 응답 p50 / p95 / p99 | 23 / 39 / 85ms | p99 67 ~ 109ms |
| 결제 응답 p50 / p95 / p99 | 24 / 38 / 62ms | p99 51 ~ 82ms |
| 일하는 DB 연결 (평균 / 최대) | 3.0 / 9개 | |

### 관찰

- **티켓 오픈에서 응답이 1초 넘게 걸린 이유는 행 잠금이 아니다.** 행 잠금을 기다리는 연결은 표본마다 거의 0이었다. 같은 좌석을 두고 부딪혀도 앞 트랜잭션이 금방 끝나 대기가 짧다. 동시에 들어온 요청 500개가 커넥션 10개와 요청 스레드를 기다리는 시간이 대부분으로 보인다. 앱 안의 대기 시간을 따로 재지 않아서 추정이다.
- 경합이 없으면 선점과 결제는 각각 p95 40ms 안팎이다. 초당 예매 50건(쓰기 요청 초당 100건)에서는 커넥션 풀이 차지 않았다.
- 7-1에서 선점 방식을 비교할 때, 지금 `rush.js`만으로는 방식 차이가 커넥션 대기에 묻힐 수 있다. 행 잠금이 실제로 경합하는 시나리오(소수 좌석에 집중, 여러 좌석 동시 선점)를 더해 비교한다.

## 4. 좌석 선점 방식 비교 (2026-11-18)

[ADR 0008](adr/0008-hold-seats-with-ordered-pessimistic-locks.md)에서 미룬 비교다. 결정은 [ADR 0010](adr/0010-keep-ordered-pessimistic-lock-for-seat-hold.md)에 있다.

### 조건

| 방식 | 선점 구현 |
| --- | --- |
| 비관적 락 (기준선) | 좌석을 `ORDER BY id`로 잠그고 읽은 뒤 상태 확인 |
| NOWAIT | 기준선과 같지만, 잠긴 좌석이 있으면 기다리지 않고 바로 `SEAT_NOT_AVAILABLE` |
| 조건부 UPDATE | `UPDATE ... WHERE status = 'AVAILABLE'` 한 문장, 바뀐 행 수로 판단 |
| 낙관적 락 | 잠그지 않고 읽고, 저장할 때 버전(`@Version`)으로 충돌 확인 |

- 시나리오: 티켓 오픈(`rush.js`, 회원 500명 → 좌석 200석, 1석씩)과 인기 좌석(`hot.js`, 회원 300명 → 좌석 60석, 2석씩 무작위 순서). 인기 좌석은 행 잠금이 실제로 부딪히게 하려고 이번에 더했다.
- 커넥션 풀: 기본값 10개. 인기 좌석은 30개로도 쟀다.
- 방식마다 앱을 새로 띄우고 워밍업한 뒤 3번씩 돌렸다. 표의 값은 중앙값이고 괄호는 3회 범위다.
- 46번 측정 모두 정합성 위반은 0건이었다. 두 번(조건부 UPDATE·풀 30개 1회에 92건, 낙관적 락·풀 30개 1회에 11건) 접속 단계 실패가 있었다. 앱 로그에 500 오류가 없어 부하 도구가 연결을 맺지 못한 것으로 보고, 해당 실행도 중앙값에 넣었다. 조건부 UPDATE·풀 30개는 확인용으로 한 번 더 쟀고(접속 실패 없음, 매진 3.0초) 중앙값에는 넣지 않았다.

### 티켓 오픈 (`rush.js`), 풀 10개

| 방식 | 매진까지 | 선점 p95 | 결제 p95 |
| --- | --- | --- | --- |
| 비관적 락 | 5.7초 (5.4 ~ 6.5) | 2,095ms | 2,175ms |
| NOWAIT | 5.4초 (4.7 ~ 5.5) | 1,916ms | 2,736ms |
| 조건부 UPDATE | 5.8초 (5.4 ~ 7.1) | 1,795ms | 2,465ms |
| 낙관적 락 | 5.4초 (5.2 ~ 6.7) | 1,859ms | 1,991ms |

네 방식의 범위가 모두 겹친다. 7-0 기준선(4.9초)보다 느린 것은 날과 PC 상태가 달라서다.

### 인기 좌석 (`hot.js`), 풀 10개

| 방식 | 매진까지 | 선점 p95 | 결제 p95 | 잠금 대기 연결 (최대) |
| --- | --- | --- | --- | --- |
| 비관적 락 | 2.4초 (2.2 ~ 2.9) | 983ms | 1,202ms | 2개 |
| NOWAIT | 1.6초 (1.6 ~ 1.8) | 627ms | 656ms | 0개 |
| 조건부 UPDATE | 2.4초 (2.4 ~ 3.9) | 918ms | 1,007ms | 2개 |
| 낙관적 락 | 3.2초 (2.7 ~ 4.0) | 1,136ms | 1,423ms | 3개 |
| 비관적 락 (세션 마지막에 다시) | 3.0초 (2.6 ~ 3.8) | 1,505ms | 1,536ms | 3개 |

같은 기준선을 세션 처음과 마지막에 재니 매진 시간이 2.4초에서 3.0초로 늘었다. 측정 순서에 따라 PC 상태가 달라지는 흔들림이 방식 차이만큼 크다는 뜻이다. 그래서 NOWAIT와 기준선만 번갈아 3번씩 다시 쟀다.

| 방식 (번갈아 측정) | 매진까지 | 선점 p95 | 결제 p95 |
| --- | --- | --- | --- |
| 비관적 락 | 3.8초 (3.4 ~ 4.2) | 2,295ms | 2,443ms |
| NOWAIT | 3.4초 (3.0 ~ 4.1) | 1,803ms | 1,425ms |

번갈아 재도 NOWAIT가 앞섰지만 차이가 줄었고, 매진 시간 범위가 겹친다.

### 인기 좌석 (`hot.js`), 풀 30개

| 방식 | 매진까지 | 선점 p95 | 잠금 대기 연결 (평균 / 최대) |
| --- | --- | --- | --- |
| 비관적 락 | 2.7초 (2.0 ~ 3.1) | 1,480ms | 1.9 / 15개 |
| NOWAIT | 2.3초 (2.2 ~ 3.0) | 1,317ms | 0.0 / 0개 |
| 조건부 UPDATE | 2.4초 (2.3 ~ 2.9) | 1,323ms | 0.5 / 5개 |
| 낙관적 락 | 2.6초 (2.2 ~ 5.0) | 1,333ms | 0.3 / 12개 |

### 관찰

- **방식 차이보다 측정 환경의 흔들림이 크다.** 티켓 오픈과 풀 30개에서는 네 방식의 범위가 겹친다.
- **인기 좌석·풀 10개에서만 NOWAIT가 꾸준히 앞섰다.** 앞 트랜잭션을 기다리지 않고 바로 실패해 커넥션을 빨리 돌려주기 때문으로 보인다. 대신 결국 실패할 트랜잭션이 잠깐 잡은 좌석도 "이미 선점됨"으로 응답한다.
- **풀을 30개로 늘려도 빨라지지 않았다.** 비관적 락은 잠금 대기가 최대 15개까지 늘었지만, 잠금 대기가 없는 NOWAIT도 똑같이 느려졌다. 잠금이 아니라 한 PC의 CPU가 한계다.
- 낙관적 락도 충돌하면 앞 트랜잭션의 행 잠금을 기다린 뒤 실패한다(잠금 대기 최대 12개). 잠그지 않고 읽는다고 대기가 사라지지는 않는다.

## 5. 회차 취소 개선 (2026-11-18)

[도메인 설계 7절](domain.md#7-받아들인-한계)에서 미룬 측정이다. 결정은 [ADR 0011](adr/0011-cancel-performance-with-set-based-updates.md)에 있다.

### 조건

- 시나리오: `cancel.js`. 확정 예매 N건(한 건에 1석)으로 매진된 회차를 관리자가 취소한다. 취소하는 동안 그 회차 회원 100명이 초당 20번 포인트를 충전하고, 관계없는 공연 목록을 초당 5번 조회한다.
- 매진 회차는 `sql/cancel.sql`이 바로 넣는다. 예매는 회원 2,000명에게 차례로 나눠 준다.
- 커넥션 풀 10개(기본값). 방식마다 앱을 새로 띄우고 200건 취소로 워밍업한 뒤 3번씩 돌렸다. 표의 값은 중앙값이다.
- 33번 측정 모두 정합성 위반 0건(환불 거래 확인 포함).

| 방식 | 구현 |
| --- | --- |
| 기존 | 예매를 한 건씩 엔티티로 읽고 바꾼다. 예매 한 건에 SQL 8개 |
| 묶어 보내기 | 엔티티는 그대로 바꾸되, 좌석은 회차 단위로 한 번에 읽고, 지갑은 1,000명씩 묶어 잠그고, 환불 거래는 JDBC 배치로 넣고, UPDATE를 100개씩 묶어 보낸다 |
| 한 문장씩 (채택) | 예매·좌석·결제는 테이블마다 UPDATE 한 문장. 지갑과 환불 거래는 묶어 보내기와 같다 |

### 취소에 걸린 시간

| 확정 예매 | 기존 | 묶어 보내기 | 한 문장씩 |
| --- | --- | --- | --- |
| 1,000건 | 21.4초 | 0.56초 | 0.26초 |
| 4,000건 | 143.1초 | 1.58초 | 0.62초 |
| 16,000건 | 재지 않음 | 5.43초 | 1.61초 |
| 50,000건 (최대) | 재지 않음 | 16.5초 | 5.02초 (3.5 ~ 5.3) |

기존 방식은 6단계 측정(4,000건 107.9초)보다 느리다. 이번에는 충전과 목록 조회를 함께 보내서다.

### 취소하는 동안 관계없는 공연 목록 조회

| --- | --- | --- | --- |
| 1,000건 | p95 9.2초, 최대 10.4초 | p95 17ms | p95 16ms |
| 4,000건 | p95 47.2초, 실패 77건 | p95 17ms, 최대 204ms | p95 16ms, 최대 28ms |

### 취소하는 동안 그 회차 회원의 충전 (최대 응답 시간)

| 확정 예매 | 기존 | 묶어 보내기 | 한 문장씩 |
| --- | --- | --- | --- |
| 1,000건 | 10.9초 | 0.3초 | 0.2초 |
| 4,000건 | 83.6초, 실패 304건 | 0.8초 | 0.4초 |
| 16,000건 | | 2.3초 | 0.7초 |
| 50,000건 | | 7.1초 | 2.4초 |

### 관찰

- **기존 방식은 앱 전체를 멈춘다.** 취소 트랜잭션이 회원 지갑을 잠근 채 오래 걸리자, 그 회원들의 충전이 지갑 잠금을 기다리며 DB 커넥션 10개 중 최대 9개를 차지했다(행 잠금 대기 연결 최대 9개). 관계없는 공연 목록 조회도 커넥션을 기다렸고, 4,000건에서는 30초(HikariCP 기본 대기 시간) 안에 커넥션을 못 받은 요청이 실패했다.
- **느린 원인은 SQL 왕복 수였다.** 묶어 보내기만으로 4,000건이 143초에서 1.6초가 됐다. 예매 한 건마다 쿼리를 보내며 영속성 컨텍스트를 매번 검사하던 비용이 사라졌다.
- **한 문장씩이 3배 빠르고, 다른 요청에 주는 영향이 훨씬 작다.** 50,000건에서 묶어 보내기는 지갑을 잠근 뒤 커밋까지 오래 걸려 목록 조회 p95가 4.8초였지만, 한 문장씩은 61ms였다.
- 두 방식 모두 최대 규모를 HTTP 시간 제한(30초) 안에 끝내, 나눠서 비동기로 처리하는 방식은 만들지 않았다.
